    Agile Cell Playbook¶

    Una metodología para crear o tomar una célula ágil y convertirla en un sistema que entrega valor de negocio de forma predecible y sostenible.

    Principio rector

    No optimizamos la actividad del equipo: optimizamos el flujo de valor desde que nace una necesidad de negocio hasta que un usuario la usa en producción y medimos si cambió algo.

    ¿Para quién es?¶

    • Scrum Masters, Agile Coaches y Delivery Leads que forman o reciben una célula.
    • Product Owners / Product Managers que necesitan un marco para descubrir y priorizar.
    • Líderes técnicos que deben asegurar fundaciones de ingeniería sanas.
    • Gerencias y áreas de compras que contratan células externalizadas y quieren gobernarlas por resultados.

    Los dos escenarios¶

    Partes desde cero: no hay equipo, quizá no hay producto. Recorres las fases 0 → 6 en orden, con foco fuerte en Descubrimiento (1) y Fundaciones técnicas (2) antes de acelerar la entrega.

    Hay un equipo trabajando, con historia, deuda y hábitos. La Fase 0 es un diagnóstico y define qué fases reforzar primero. No se rehace todo: se estabiliza el flujo y luego se mejora.

    Si la célula pasa de un proveedor a un equipo interno, sigue además el capítulo de Traspaso a equipo interno.

    Mapa de la metodología¶

    flowchart LR
    F0[0 · Diagnóstico<br/>y onboarding] --> F1[1 · Descubrimiento<br/>de producto]
    F1 --> F2[2 · Fundaciones<br/>técnicas]
    F2 --> F3[3 · Sistema<br/>de trabajo]
    F3 --> F4[4 · Entrega<br/>continua]
    F4 --> F5[5 · Medición y<br/>aprendizaje]
    F5 --> F6[6 · Mejora e<br/>innovación]
    F6 -. nuevas hipótesis .-> F1
    F5 -. ajuste del sistema .-> F3
    G[Transversal · Gobierno con proveedores] -.- F0 & F3 & F5
    T[Transversal · Traspaso<br/>a equipo interno] -.- G
    T -. reinicia con<br/>equipo interno .-> F0

    Las fases son secuenciales al arrancar y cíclicas en régimen: una vez la célula está en marcha, las fases 1 a 6 conviven en paralelo como ciclos de distinto ritmo (descubrimiento continuo, entrega continua, mejora continua).

    Marcos que integra¶

    Marco Para qué lo usamos
    Lean Eliminar desperdicio, ver el flujo de valor completo, limitar el WIP
    Kanban Gestionar el flujo, hacer visibles las políticas, medir lead time y throughput
    Scrum Cadencia, compromiso con objetivos de sprint, inspección y adaptación
    Lean Startup Validar hipótesis de negocio con el menor esfuerzo (Construir–Medir–Aprender)
    MVO / MVP Definir el resultado mínimo que valida una apuesta y el producto mínimo para lograrlo
    User Story Mapping Ordenar el backlog según el recorrido del usuario y cortar releases con sentido
    Management 3.0 Autoorganización, delegación explícita, motivación y salud del equipo
    C4 + ADR Comunicar y decidir arquitectura de forma liviana y trazable
    CI/CD + Docker Entregar en lotes pequeños, frecuentes y con bajo riesgo
    DORA Medir el desempeño de entrega de software

    Cómo está organizada cada fase¶

    Todas las fases siguen la misma plantilla para que sean fáciles de recorrer y auditar:

    1. Objetivo de negocio de la fase.
    2. Entradas necesarias.
    3. Actividades paso a paso.
    4. Artefactos que se producen.
    5. Métricas que indican si la fase funciona.
    6. Roles involucrados (RACI liviano).
    7. Criterios de salida: checklist para pasar a la siguiente.
    8. Antipatrones frecuentes.

    Tiempos de referencia¶

    Fase Crear (célula nueva) Tomar (célula existente)
    0 · Diagnóstico y onboarding 1–2 semanas 2–3 semanas
    1 · Descubrimiento 2–6 semanas (hasta validar MVO) 1–2 semanas de revisión
    2 · Fundaciones técnicas 2–4 semanas (sprint 0 extendido) Plan de remediación incremental
    3 · Sistema de trabajo 1 semana + ajuste continuo 1–2 semanas
    4 · Entrega continua Continua Continua
    5 · Medición Línea base en 4–6 semanas Línea base en 2 semanas (hay historia)
    6 · Mejora e innovación Continua desde el mes 2 Continua

    Un traspaso de proveedor a equipo interno suma de 3 a 6 meses antes de que el equipo interno retome la Fase 0.

    Los tiempos son referencia, no compromiso

    Una fase termina cuando cumple sus criterios de salida, no cuando vence el plazo.

    Principios de uso¶

    • Adapta, no adoptes. Cada célula tiene su contexto. Registra las adaptaciones como ADRs de proceso.
    • Empieza por donde duele. En una célula existente, el diagnóstico decide el orden.
    • Lotes pequeños también para la guía. No implementes todas las herramientas a la vez; introduce una o dos por iteración.
    • Mide antes de cambiar. Toma una línea base antes de cualquier intervención para poder demostrar mejora.

    Fase 0 · Diagnóstico y onboarding¶

    Objetivo de negocio¶

    Entender el contexto de negocio, el estado real de la célula (si existe) y establecer los acuerdos mínimos para que el equipo trabaje como una unidad orientada a resultados.

    Entradas¶

    • Patrocinador de negocio identificado y con disponibilidad.
    • Objetivo estratégico al que contribuye el producto (OKR, meta del área).
    • Modelo de contratación: equipo propio, externalizado o mixto.
    • Si la célula viene de un proveedor: traspaso a equipo interno cerrado o, al menos, en operación autónoma.
    • Si la célula existe: acceso a Jira/Azure DevOps, repositorios, pipelines, monitoreo y documentación.

    Actividades¶

    0.1 Entender el negocio¶

    1. Entrevista con el patrocinador: ¿qué problema existe?, ¿cuánto cuesta no resolverlo?, ¿cómo se ve el éxito en 6 y 12 meses?
    2. Mapear stakeholders en una matriz poder / interés (ver mapa de stakeholders).
    3. Identificar las restricciones duras: regulatorias, presupuestarias, de fechas, tecnológicas.

    0.2 Diagnóstico de madurez (solo célula existente)¶

    Aplicar el assessment de madurez en 2–3 semanas combinando datos (historial de Jira, pipelines, incidentes) y conversaciones (1:1, observación de ceremonias). Son 30 preguntas en seis dimensiones, con criterios observables para cada nivel:

    Dimensión Qué evalúa
    Producto Conexión del backlog con el negocio, medición de impacto, hipótesis, roadmap, contacto con usuarios
    Flujo Visibilidad, límites de WIP, previsibilidad, trabajo no planificado, bloqueos
    Ingeniería Integración continua, despliegue, ambientes, arquitectura, observabilidad
    Calidad Automatización de pruebas, rol de QA, defectos escapados, DoD, incidentes
    Equipo Estabilidad, autoorganización, seguridad psicológica, mejora continua, conocimiento
    Relación con negocio Autoridad del PO, patrocinio, revisiones, planificación, modelo de gobierno

    El equipo se autoevalúa y el facilitador puntúa lo observado. La calculadora de madurez genera el radar con ambas miradas, marca las brechas de percepción y propone el orden de fases según las reglas de priorización.

    Datos del pasado

    En célula existente, extrae al menos 3 meses de historial de tickets para calcular lead time, throughput y WIP de línea base. El Agile Metric Hub puede servir para cruzar sprints.

    0.3 Formar o reconocer el equipo¶

    1. Confirmar roles y dedicación real (no "50 % en tres proyectos").
    2. Taller de Team Canvas (2 h): propósito, valores, metas, roles, reglas, necesidades.
    3. Taller de Moving Motivators (Management 3.0) para conocer qué motiva a cada persona.
    4. Construir el Delegation Board: qué decide el equipo, qué decide el PO, qué decide la gerencia, en los 7 niveles de delegación.
    5. Si hay equipo externo: sesión conjunta cliente–proveedor para alinear expectativas (ver Gobierno con proveedores).

    0.4 Acuerdos mínimos de arranque¶

    • Canales de comunicación y horarios de solapamiento (en equipos distribuidos, ver acuerdos de trabajo distribuido).
    • Cadencia inicial de ceremonias (se refina en Fase 3).
    • Accesos y herramientas para todas las personas desde el día 1.

    Artefactos¶

    Artefacto Plantilla
    Mapa de stakeholders Plantilla
    Assessment de madurez (radar) Cuestionario y calculadora
    Team Canvas Plantilla
    Delegation Board Plantilla
    Plan de onboarding por persona Plantilla

    Métricas¶

    • Tiempo hasta que una persona nueva hace su primer commit en producción (time to first deploy).
    • Porcentaje de accesos y herramientas disponibles el día 1.
    • Línea base de lead time, throughput y WIP (célula existente).

    Roles¶

    Actividad Patrocinador PO Scrum Master / Coach Equipo Proveedor
    Entender el negocio A R C I I
    Assessment I C R/A C C
    Team Canvas y Delegation Board C R A R R

    R = responsable, A = aprueba, C = consultado, I = informado.

    Criterios de salida¶

    • Objetivo de negocio del producto escrito en una frase y aceptado por el patrocinador.
    • Assessment completado, con brechas conversadas y orden de fases acordado (célula existente).
    • Team Canvas y Delegation Board publicados y visibles.
    • Roles con dedicación real confirmada.
    • Todas las personas con accesos completos.

    Antipatrones¶

    • Saltarse el diagnóstico e imponer el marco "de siempre" en una célula existente.
    • Patrocinador ausente: sin dueño de negocio, el equipo optimiza actividad, no valor.
    • Equipo de nombre: personas repartidas en varios proyectos sin dedicación real.
    • Proveedor tratado como "fábrica" al que se le entregan especificaciones cerradas.

    Fase 1 · Descubrimiento de producto¶

    Objetivo de negocio¶

    Reducir la incertidumbre antes de invertir en construcción: definir el problema, las hipótesis de valor y el MVO (Minimum Viable Outcome), y traducirlo a un backlog ordenado por el recorrido del usuario.

    MVO y MVP

    • MVO (Minimum Viable Outcome): el cambio mínimo y medible en el comportamiento del usuario o del negocio que valida la apuesta. Ejemplo: 20 % de los clientes que solicitan un crédito lo completan sin llamar al call center.
    • MVP (Minimum Viable Product): el vehículo mínimo que construimos para intentar lograr ese outcome.

    Primero se define el MVO; el MVP se diseña para alcanzarlo. Un MVP sin MVO es solo una versión pequeña del producto.

    Ejemplo completo en el caso Crear una célula.

    Entradas¶

    • Objetivo de negocio de la Fase 0.
    • Acceso a usuarios reales o sus representantes.
    • Datos existentes: analítica, tickets de soporte, encuestas.

    Actividades¶

    1.1 Entender el problema¶

    1. Entrevistas de problema con 5–8 usuarios (no se presenta la solución).
    2. Mapear el journey actual y sus puntos de dolor.
    3. Completar el Lean Canvas con el patrocinador y el PO.

    1.2 Conectar negocio con producto: Impact Mapping¶

    flowchart LR
    G((Meta de negocio)) --> A1[Actor: cliente nuevo]
    G --> A2[Actor: ejecutivo de ventas]
    A1 --> I1[Impacto: completa la solicitud sin ayuda]
    A2 --> I2[Impacto: dedica menos tiempo a trámites]
    I1 --> E1[Entregable: formulario guiado]
    I1 --> E2[Entregable: validación automática de documentos]
    I2 --> E3[Entregable: panel de solicitudes]

    Cada entregable del backlog debe poder rastrearse hasta una meta de negocio. Si no se puede, se cuestiona.

    1.3 Formular hipótesis¶

    Formato: Creemos que [entregable] para [actor] logrará [impacto]. Sabremos que es cierto cuando veamos [métrica] alcanzar [umbral] en [plazo].

    Priorizar hipótesis por riesgo × valor y validar primero las más riesgosas con el experimento más barato posible (prototipo, fake door, Mago de Oz, concierge).

    Cuando hay que ordenar entregables ya validados que compiten por la misma capacidad, usar Cost of Delay y WSJF para hacer explícito el costo económico de esperar.

    1.4 User Story Map¶

    1. Definir la columna vertebral: actividades del usuario de izquierda a derecha.
    2. Bajo cada actividad, listar tareas e historias.
    3. Trazar líneas horizontales de release: la primera línea es el MVP que persigue el MVO.
    4. Validar el mapa con usuarios y equipo técnico.

    Ver plantilla de User Story Map.

    1.5 Roadmap por outcomes¶

    Roadmap en formato Ahora / Siguiente / Después, expresado en problemas y outcomes, no en fechas y funcionalidades. Ver plantilla de roadmap por outcomes.

    Artefactos¶

    Artefacto Plantilla
    Lean Canvas Plantilla
    Impact Map Diagrama de esta página
    Backlog de hipótesis Plantilla
    User Story Map con releases Plantilla
    Roadmap Ahora / Siguiente / Después Plantilla

    Métricas¶

    • Número de hipótesis validadas / invalidadas por mes (aprender rápido es éxito).
    • Costo y tiempo por experimento.
    • Porcentaje del backlog trazable a una meta de negocio.
    • Cuando el MVP esté en producción: la métrica del MVO.

    Roles¶

    Actividad Patrocinador PO Equipo UX SM / Coach
    Lean Canvas C R/A C C F
    Hipótesis y experimentos I A R R F
    User Story Map I A R R F

    F = facilita.

    Criterios de salida¶

    • MVO definido con métrica, umbral y plazo.
    • Hipótesis más riesgosa validada o descartada con evidencia.
    • User Story Map con la primera línea de release acordada.
    • Roadmap por outcomes aprobado por el patrocinador.
    • Backlog de las primeras 2–4 semanas refinado y estimado (o dimensionado).

    Antipatrones¶

    • El backlog es una lista de funcionalidades pedidas por stakeholders sin hipótesis detrás.
    • MVP que nunca es mínimo: se agregan funcionalidades "por si acaso".
    • Descubrimiento como fase única: después del arranque, debe volverse continuo.
    • Validar con opiniones internas en vez de con usuarios reales.

    Fase 2 · Fundaciones técnicas¶

    Objetivo de negocio¶

    Que el costo y el riesgo de llevar un cambio a producción sean bajos y predecibles. Sin estas fundaciones, cada entrega es cara y lenta, y el negocio deja de experimentar.

    Entradas¶

    • MVP y primera línea de release del User Story Map.
    • Restricciones técnicas y de seguridad de la organización.
    • Stack tecnológico existente (célula existente) o lineamientos corporativos.

    Actividades¶

    2.1 Arquitectura con el modelo C4¶

    Documentar solo los niveles que aportan, como código (Mermaid o Structurizr) y versionados en el repo del producto.

    Nivel 1 · Contexto: el sistema, sus usuarios y los sistemas externos.

    flowchart TB
    U[Cliente<br/><i>persona</i>] --> S[Producto<br/><i>sistema</i>]
    E[Ejecutivo<br/><i>persona</i>] --> S
    S --> P[Pasarela de pagos<br/><i>sistema externo</i>]
    S --> C[CRM corporativo<br/><i>sistema externo</i>]

    Nivel 2 · Contenedores: aplicaciones, APIs, bases de datos y cómo se comunican.

    flowchart LR
    W[Web App<br/>React] -->|HTTPS/JSON| A[API<br/>Node / Java]
    A --> DB[(Base de datos<br/>PostgreSQL)]
    A --> Q[[Cola de mensajes]]
    Q --> WK[Worker]
    WK --> C[CRM]

    Los niveles 3 (componentes) y 4 (código) solo se documentan para partes críticas o complejas.

    2.2 Decisiones de arquitectura (ADR)¶

    Toda decisión difícil de revertir se registra como ADR en docs/adr/ del repo del producto: contexto, decisión, alternativas y consecuencias. Ver plantilla ADR.

    2.3 Dockerización¶

    • Cada servicio tiene su Dockerfile (multi-stage, imagen base mínima, usuario no root).
    • docker-compose.yml para levantar el entorno completo en local con un solo comando.
    • Las imágenes se construyen una vez en CI y la misma imagen se promueve entre ambientes (build once, deploy many).
    • Configuración por variables de entorno; secretos en un gestor de secretos, nunca en la imagen.

    flowchart LR
    C[Commit / PR] --> B[Build]

    SA --> IMG[Imagen Docker<br/>+ escaneo]
    IMG --> DEV[Deploy DEV]
    DEV --> IT[Tests de integración<br/>y contrato]

    PROD --> MON[Monitoreo<br/>+ alertas]

    Reglas mínimas:

    • Trunk-based development o ramas de vida corta (menos de 2 días).
    • El pipeline corre en cada PR; no se integra código con pipeline en rojo.
    • Pipeline completo hasta staging en menos de 15 minutos como meta.
    • Feature flags para separar despliegue de liberación.
    • Controles de seguridad en el pipeline (secretos, dependencias, imágenes) que generan evidencia para auditoría. Ver seguridad en el flujo.

    2.5 Estrategia de QA¶

    Calidad integrada en el flujo, no como fase al final. Pirámide de pruebas:

    Nivel Proporción Quién Cuándo
    Unitarias Base amplia Desarrolladores En cada commit
    Integración / contrato Media Desarrolladores + QA En cada PR
    E2E (flujos críticos) Pocas QA En staging
    Exploratorias Por historia QA + PO Antes de cerrar la historia
    No funcionales (carga, seguridad) Periódicas QA + DevOps Por release o mensualmente

    El rol de QA se transforma: de "probar al final" a definir criterios de aceptación con el PO (BDD / three amigos) y automatizar.

    2.6 Ambientes y observabilidad¶

    • Ambientes mínimos: local, DEV, QA/Staging, PROD. Lo más parecidos posible entre sí (infraestructura como código).
    • Logs estructurados, métricas técnicas y trazas desde el primer despliegue.
    • Alertas sobre síntomas que afectan al usuario, no sobre cada métrica.

    Fase 3 · Diseño del sistema de trabajo¶

    Objetivo de negocio¶

    Diseñar cómo fluye el trabajo para que el negocio reciba valor de forma predecible, con el mínimo de esperas, interrupciones y retrabajo.

    Entradas¶

    • Assessment de Fase 0 (célula existente).
    • Tipos de demanda que recibe la célula.
    • Backlog inicial de Fase 1.

    Actividades¶

    3.1 Analizar la demanda¶

    Clasificar el trabajo que llega durante 2–4 semanas (o desde el historial):

    Tipo de demanda Ejemplo Naturaleza

    Experimentos Validación de hipótesis Planificable, alta incertidumbre
    Soporte / incidentes Errores en producción No planificable, urgente
    Hotfix Corrección crítica No planificable, expedita
    Deuda técnica / mejora Refactor, actualización de librerías Planificable

    3.3 Diseñar el tablero¶

    1. Mapear el flujo de valor real (value stream): desde la idea hasta producción y validación (ver Value Stream Mapping).

    3. Límites de WIP por columna (punto de partida: número de personas en la etapa × 1,5, luego ajustar).
    4. Clases de servicio: Expedito, Fecha fija, Estándar, Intangible (deuda, mejora). El perfil de Cost of Delay de cada ítem indica su clase.
    5. Carriles (swimlanes) por tipo de demanda si aplica.

    Ejemplo de flujo:

    Opciones → Refinado (listo) → En desarrollo → Code review → En QA → Listo para prod → En producción → Validado

    Fase 4 · Entrega continua de valor¶

    Objetivo de negocio¶

    Llevar valor a producción en lotes pequeños, con frecuencia y bajo riesgo, y confirmar con datos que el valor llegó al usuario.

    Entradas¶

    • Fundaciones técnicas operativas (Fase 2).
    • Sistema de trabajo definido (Fase 3).
    • Backlog refinado y conectado a outcomes (Fase 1).

    Actividades¶

    4.1 Ciclo de vida de un ítem¶

    sequenceDiagram
    participant PO
    participant Dev as Equipo
    participant QA
    participant CI as Pipeline
    participant Prod as Producción
    PO->>Dev: Historia con criterios de aceptación (three amigos)
    Dev->>Dev: Desarrollo + pruebas unitarias
    Dev->>CI: Pull request
    CI-->>Dev: Build, tests, análisis
    Dev->>Dev: Code review
    CI->>QA: Despliegue en staging
    QA->>QA: Pruebas exploratorias + E2E
    QA->>PO: Validación funcional
    PO->>Prod: Liberación (feature flag o despliegue)
    Prod-->>PO: Métricas de uso y del outcome

    4.2 Trabajar en lotes pequeños¶

    • Historias que se completan en 1 a 3 días. Si es más grande, se divide (por flujo, regla de negocio, datos, interfaz, rendimiento).
    • Un ítem empieza solo si hay capacidad dentro del WIP: dejar de empezar, empezar a terminar.
    • Swarming: ante un bloqueo, el equipo se junta para destrabar antes de tomar algo nuevo.

    4.3 Estrategias de liberación¶

    Estrategia Cuándo usarla Riesgo
    Despliegue directo Cambios pequeños y bien probados Bajo con buen pipeline
    Feature flag Separar despliegue de liberación; probar con grupos Muy bajo
    Canary Cambios de alto riesgo; liberar a un % del tráfico Bajo
    Blue / Green Cambios de infraestructura; rollback instantáneo Bajo, más costo
    Ventana de mantenimiento Migraciones de datos irreversibles Alto, minimizar su uso

    4.4 Paso a producción¶

    Cada paso a producción sigue el checklist de paso a producción. La evidencia de seguridad que genera el pipeline (seguridad en el flujo) es la que sostiene la aprobación automática ante auditoría. En organizaciones con comité de cambios (CAB), la meta es demostrar con datos (change failure rate bajo, rollback probado) que los cambios estándar pueden aprobarse de forma automática.

    4.5 Gestión de incidentes y hotfix¶

    1. Un incidente en producción entra como Expedito: se salta la fila, respeta el WIP expedito (máximo 1).
    2. Hotfix por el mismo pipeline (no se salta pruebas; se usan pruebas focalizadas).
    3. Postmortem sin culpa dentro de 5 días hábiles para incidentes severos, con acciones en el backlog.

    4.6 Revisión con negocio¶

    En la Sprint Review o revisión de entrega se muestra software funcionando en producción y, cuando existen, los datos de uso. La pregunta clave no es "¿qué hicimos?" sino "¿qué aprendimos y qué cambia en el roadmap?".

    Checklist de paso a producción Plantilla
    Postmortems Repo del producto

    Métricas¶

    • DORA: frecuencia de despliegue, lead time de cambios, change failure rate, tiempo de recuperación.
    • Lead time y cycle time por tipo de ítem.
    • Throughput semanal.
    • Porcentaje de ítems liberados que tienen métrica de uso.

    Antipatrones¶

    • Big bang release trimestral con semanas de estabilización.

    • Review como demo de PowerPoint sin software real.

    Fase 5 · Medición y aprendizaje¶

    Objetivo de negocio¶

    Saber, con datos, si la célula está entregando valor, si lo hace de forma predecible y sostenible, y usar esa información para decidir.

    Cuatro preguntas, cuatro familias de métricas

    1. ¿Estamos generando impacto? → métricas de outcome.
    2. ¿Fluye el trabajo? → métricas de flujo.
    3. ¿Entregamos con calidad y seguridad? → métricas DORA y de calidad.
    4. ¿Es sostenible para las personas? → métricas de salud del equipo.

    Entradas¶

    • MVO y outcomes del roadmap (Fase 1).
    • Pipeline y monitoreo operativos como fuente de datos DORA (Fase 2).
    • Tablero con estados y políticas explícitas como fuente de datos de flujo (Fase 3).
    • Célula existente: al menos 3 meses de historial de tickets.

    Actividades¶

    5.1 Definir el set mínimo¶

    No medir todo. Empezar con una o dos métricas por familia, ver el catálogo de métricas.

    Familia Métricas iniciales recomendadas
    Outcome Métrica del MVO + 1 KPI de negocio del roadmap
    Flujo Lead time (percentil 85) y throughput semanal
    Entrega Frecuencia de despliegue y change failure rate
    Equipo Happiness Door o encuesta de pulso quincenal

    5.2 Tomar la línea base¶

    Antes de intervenir, medir 4–6 semanas (o extraer historial). Sin línea base no se puede demostrar mejora.

    5.3 Visualizar¶

    • Diagrama de flujo acumulado (CFD): muestra WIP, cuellos de botella y estabilidad.
    • Scatterplot de cycle time con percentiles 50, 85 y 95.
    • Histograma de throughput para pronósticos.
    • WIP aging: ítems que superan el percentil 85 se discuten en la daily.

    5.4 Pronosticar con datos¶

    Reemplazar la estimación en horas por pronósticos probabilísticos:

    • ¿Cuándo estará listo este ítem? → "85 % de los ítems terminan en 8 días o menos".
    • ¿Cuánto entregaremos en 6 semanas? → simulación de Monte Carlo con el throughput histórico.
    • ¿Cuándo termina este release de 40 ítems? → Monte Carlo con rango de fechas y probabilidad.

    Usa el pronóstico Monte Carlo para calcularlo en el navegador con tu throughput histórico.

    5.5 Medir la salud del equipo (Management 3.0)¶

    • Happiness Door: al final de la retro, cada persona marca su estado. Tendencias, no números absolutos.
    • Moving Motivators cada 3–6 meses: ¿cambió lo que motiva al equipo?
    • Kudo Cards: reconocimiento entre pares visible.
    • Rotación voluntaria y ausentismo (vía RR. HH. o proveedor).

    5.6 Usar las métricas para decidir¶

    Las métricas se revisan en:

    • Daily: WIP aging y bloqueos.
    • Retrospectiva: tendencias de flujo y calidad (retro basada en datos).
    • Revisión de servicio mensual: métricas contra niveles de servicio acordados.
    • Revisión con negocio: outcomes y decisiones de roadmap (perseverar, pivotar o parar).

    Dashboard de outcomes Herramienta de analítica de producto

    Métricas¶

    Esta fase mide la calidad del propio sistema de medición:

    • Porcentaje del set mínimo con dato actualizado, dueño y fuente automática.
    • Decisiones registradas por trimestre que se basaron en métricas.
    • Acierto de los pronósticos: porcentaje de entregas que caen dentro del rango pronosticado.

    • Velocity como meta o para comparar equipos.

    Fase 6 · Mejora, innovación y escalamiento¶

    Objetivo de negocio¶

    Que la célula mejore de forma sostenida su capacidad de entregar valor, genere nuevas oportunidades de negocio y pueda crecer o replicarse sin perder lo logrado.

    Entradas¶

    • Métricas con línea base y tendencias (Fase 5).
    • Acciones de retrospectivas y postmortems.
    • Portafolio de hipótesis (Fase 1).
    • Assessment de madurez anterior, para comparar la evolución.

    Actividades¶

    6.1 Mejora continua (Kaizen)¶

    • Backlog de mejora visible junto al backlog de producto, con capacidad reservada.
    • Cada mejora se formula como experimento: si cambiamos X, esperamos que la métrica Y pase de A a B en N semanas.
    • Herramientas de análisis: 5 porqués, diagrama de Ishikawa, análisis de bloqueos (blocker clustering), mapa de flujo de valor futuro.
    • Máximo 1 a 2 mejoras en curso a la vez (WIP también para la mejora).

    6.2 Value Stream Mapping¶

    Cada 3–6 meses, mapear el flujo de valor completo (de la idea al usuario) con la plantilla de Value Stream Mapping y calcular:

    • Eficiencia de flujo = tiempo de trabajo activo ÷ lead time total. En la mayoría de las organizaciones es menor al 15 %; el desperdicio está en las esperas, no en el trabajo.
    • Dónde están las mayores esperas (aprobaciones, dependencias, ambientes, QA).

    6.3 Innovación¶

    Práctica Descripción Frecuencia
    Hackathon / Innovation day Tiempo libre para explorar ideas del equipo Trimestral
    Portafolio de experimentos Ideas con hipótesis, priorizadas por valor y riesgo Continuo
    Descubrimiento continuo Entrevistas semanales con usuarios por el trío PO + Diseño + Tech Lead Semanal
    Revisión de apuestas Perseverar, pivotar o parar cada iniciativa según datos Trimestral

    6.4 Management 3.0 para la evolución del equipo¶

    • Revisar el Delegation Board: a medida que crece la madurez, más decisiones pasan al equipo.
    • Celebration Grid: celebrar aprendizajes (experimentos fallidos incluidos), no solo éxitos.
    • Personal Maps para fortalecer relaciones, especialmente en equipos distribuidos o mixtos cliente–proveedor.
    • Planes de crecimiento individual y de habilidades en forma T.

    6.5 Escalamiento¶

    Antes de agregar personas, verificar:

    1. ¿El cuello de botella está dentro de la célula? (Si está fuera, más personas no ayudan.)
    2. ¿Las fundaciones técnicas soportan más equipos trabajando en paralelo?
    3. ¿El producto se puede dividir en dominios con poca dependencia?

    Si se crea una segunda célula:

    • Dividir por dominio o flujo de valor, no por capa técnica.
    • Sembrar la nueva célula con 1–2 personas de la célula madura.
    • Coordinar con cadencias livianas (sincronización de PO, revisión de operaciones conjunta, tablero de dependencias).
    • Reutilizar esta guía desde la Fase 0.

    Aplica cuando la célula es externalizada o mixta. El reto es pasar de un modelo "fábrica de software" (horas y especificaciones cerradas) a una alianza por resultados sin perder control.

    Protección del conocimiento¶

    • Código, documentación, ADRs y pipelines en repositorios del cliente.
    • DoD incluye documentación mínima y pruebas automatizadas.
    • Plan de salida (exit plan) definido en el contrato: traspaso, periodo de traslape, propiedad intelectual. Su ejecución se describe en Traspaso a equipo interno.
    • Activos (cuentas cloud, dominios, licencias, secretos) a nombre del cliente desde el primer día.
    • Rotación planificada con al menos 2 semanas de traslape (ver plan de onboarding y offboarding).
    • Reglas explícitas sobre el uso de herramientas de IA por parte del proveedor (ver IA en la célula).

    Criterios de salida¶

    El gobierno está establecido cuando:

    • Modelo de contratación elegido y justificado.
    • Product Owner del lado del cliente con dedicación real.
    • Niveles de servicio basados en flujo acordados, con línea base y fuente de datos.
    • Cadencias de gobierno en el calendario de ambas partes.
    • Código, pipelines, documentación y activos en cuentas del cliente.
    • Plan de salida incluido en el contrato.

    Antipatrones¶

    • Medir al proveedor por horas imputadas.
    • Especificaciones cerradas que impiden aprender durante la construcción.
    • "Nosotros y ellos": ceremonias separadas para cliente y proveedor.
    • Dependencia total del conocimiento del proveedor, sin acceso a código ni documentación.

    Transversal · Traspaso de proveedor a equipo interno¶

    Aplica cuando una célula externalizada o mixta pasa a manos de un equipo interno (insourcing), total o parcialmente. Es la ejecución del plan de salida definido en Gobierno con proveedores y una variante exigente de la ruta Tomar: el equipo que recibe no existe o es nuevo, y el equipo que conoce el sistema se va.

    Principio del traspaso

    No se traspasa un sistema: se traspasa la capacidad de cambiarlo con seguridad. El traspaso termina cuando el equipo interno lleva cambios a producción y resuelve incidentes sin ayuda, no cuando vence el contrato.

    Objetivo de negocio¶

    Transferir la operación y la evolución del producto al equipo interno sin interrumpir el flujo de valor ni degradar la calidad en producción, y dejar al cliente con control total sobre el código, la infraestructura, los datos y el conocimiento.

    Entradas¶

    • Decisión de traspaso aprobada por el patrocinador, con fecha objetivo y alcance (total, parcial o por dominio).
    • Contrato vigente con su plan de salida: periodo de traslape, entregables, propiedad intelectual y continuidad del servicio.
    • Equipo interno identificado, aunque esté incompleto, y presupuesto para contratar lo que falte.
    • Assessment de madurez reciente de la célula (si no existe, se aplica en la etapa 1).
    • Línea base de métricas de flujo, DORA y calidad (ver Fase 5).

    Actividades¶

    T.1 Preparar el traspaso¶

    1. Inventario de activos: repositorios, pipelines, ambientes, cuentas cloud, dominios, certificados, secretos, licencias, herramientas SaaS, bases de datos y backups. Para cada activo: dónde vive, quién es dueño y si está a nombre del cliente.
    2. Transferir la propiedad antes que el conocimiento: todo activo que esté a nombre del proveedor pasa al cliente en esta etapa, y se rotan las credenciales compartidas.
    3. Mapa de conocimiento: listar dominios funcionales, componentes técnicos y procesos operativos (despliegue, monitoreo, guardias, cierres de mes), con quién los domina hoy y quién los recibirá. Ver plan de traspaso.
    4. Brechas de documentación: verificar que existan diagramas C4, ADRs, runbooks, DoR/DoD y políticas del tablero. Lo que falte se produce durante el shadowing, escrito por el equipo interno y revisado por el proveedor.
    5. Plan de personas: perfiles necesarios, contrataciones, y si alguna persona del proveedor se incorporará al cliente (revisar cláusulas contractuales).
    6. Congelar el riesgo, no el producto: acordar con el PO qué cambios de alto riesgo (migraciones, cambios de arquitectura) se adelantan o posponen para no coincidir con el cambio de manos.

    T.2 Shadowing: el equipo interno observa¶

    • Equipo interno y proveedor trabajan en el mismo tablero y las mismas ceremonias. No hay un tablero de traspaso separado.
    • Cada persona interna tiene una contraparte en el proveedor por área de conocimiento.
    • El equipo interno participa en refinamientos, code reviews, despliegues e incidentes como observador activo.
    • Sesiones de transferencia sobre trabajo real, no presentaciones: recorrer el código de una historia en curso, un despliegue o un postmortem.
    • El equipo interno levanta su entorno local de cero y despliega un cambio trivial a staging (walking skeleton del traspaso).

    T.3 Reverse shadowing: el equipo interno ejecuta¶

    • El equipo interno toma historias reales y las lleva a producción; el proveedor revisa pull requests y despliegues.
    • El equipo interno entra a la guardia con el proveedor como segundo nivel.
    • Se practica al menos un rollback y un restore de backup conducidos por el equipo interno.
    • Cada sesión de transferencia termina con un artefacto actualizado (runbook, ADR, diagrama) en el repositorio del cliente.

    T.4 Operación autónoma con respaldo¶

    • El equipo interno opera solo. El proveedor queda disponible a demanda con un tiempo de respuesta acordado y un tope de horas.
    • Cada consulta al proveedor se registra: qué se preguntó y qué documentación faltaba. Es el mejor indicador de lo que el traspaso no cubrió.
    • Se revisan las métricas contra la línea base en la revisión de servicio.

    T.5 Cierre y salida¶

    1. Verificar que el inventario de activos está completo, a nombre del cliente y con credenciales rotadas.
    2. Retirar los accesos del proveedor a todos los sistemas.
    3. Cerrar formalmente el contrato: entregables recibidos, propiedad intelectual y garantías.
    4. Retrospectiva de traspaso con ambos equipos: qué funcionó, qué aprendimos para el próximo.
    5. Volver a aplicar el assessment de madurez y retomar el ciclo desde la Fase 0 con el equipo interno.

    T.6 Cuidar a las personas¶

    • El equipo saliente pierde el incentivo a transferir: acordar con el proveedor bonos o hitos de pago ligados a los criterios de traspaso, no a la fecha.
    • Explicitar al equipo interno qué decide desde el primer día y cómo cambia con el tiempo en el Delegation Board.
    • Hacer un nuevo Team Canvas cuando el equipo interno queda solo: es otro equipo.

    Transversal · IA en la célula¶

    Aplica cuando la célula usa asistentes de código o agentes de IA en cualquier fase. En 2026 la pregunta ya no es si usarlos, sino cómo hacerlo sin perder calidad, seguridad ni aprendizaje, y cómo saber si de verdad mejoran el flujo de valor.

    Principio

    La IA cambia quién escribe el primer borrador, no quién responde por el resultado. La persona que integra un cambio es responsable de él, lo haya escrito ella o una herramienta.

    Objetivo de negocio¶

    Usar la IA para acortar el lead time y mejorar la calidad del producto, con riesgos de seguridad, propiedad intelectual y dependencia controlados, y con evidencia medida contra una línea base, no con percepciones.

    Entradas¶

    • Política de la organización sobre uso de IA: herramientas aprobadas, datos permitidos, licencias.
    • Línea base de métricas de flujo, DORA y calidad (ver Fase 5).
    • DoD vigente y reglas de revisión de código (ver DoR / DoD).
    • Contrato con el proveedor, si la célula está externalizada.

    Actividades¶

    IA.1 Elegir casos de uso por fase¶

    Empieza por uno o dos casos de uso, no por todos:

    Fase Caso de uso Cuidado
    1 · Descubrimiento Síntesis de entrevistas y agrupación de hallazgos Anonimiza antes; valida la síntesis contra las notas originales
    2 · Fundaciones Generación de pruebas, borradores de diagramas C4 y ADRs El ADR registra una decisión humana; la IA redacta, no decide
    4 · Entrega Asistentes en el editor, apoyo en la revisión de PRs Revisión humana obligatoria; ver IA.2
    5 · Medición Análisis de datos de flujo, consultas sobre el tablero Verifica cálculos y fuentes antes de decidir

    IA.2 Ajustar la DoD y la revisión de código¶

    Agrega a la DoD:

    • La persona que abre el PR entiende y puede explicar todo el código, incluido el generado.
    • Todo código generado pasó por revisión humana, igual que el escrito a mano.
    • El código generado tiene pruebas; las pruebas generadas se revisaron para confirmar que prueban algo útil.
    • Sin secretos, datos reales ni código de terceros con licencia incompatible.

    IA.3 Seguridad y propiedad intelectual¶

    • Usa solo herramientas aprobadas por la organización, con condiciones que impidan entrenar modelos con tus datos.
    • Define qué no se comparte con herramientas externas: datos personales, datos de clientes, secretos, código clasificado como confidencial.
    • Activa el control de licencias de dependencias y, si la herramienta lo ofrece, el filtro de coincidencias con código público.
    • Los agentes que ejecutan acciones (abrir PRs, correr comandos) operan con permisos mínimos y nunca con credenciales de producción.
    • El código generado pasa por los mismos controles del pipeline. Ver Seguridad en el flujo.

    IA.4 Medir el efecto como un experimento¶

    Trata la adopción como una hipótesis de la Fase 6: Creemos que usar asistentes en la revisión de PRs reducirá el tiempo de revisión sin aumentar el change failure rate. Lo sabremos en 8 semanas.

    • Toma la línea base antes de empezar y compara antes y después.
    • Mira resultados del sistema: lead time, change failure rate, defectos escapados, tiempo de revisión, tamaño de PR.
    • No midas líneas de código generadas, sugerencias aceptadas ni "horas ahorradas" autodeclaradas: son métricas de vanidad.
    • Espera varias semanas: el primer mes suele mezclar curva de aprendizaje y entusiasmo.

    IA.5 Controlar el tamaño de lote¶

    Más código no es más valor. Si es fácil generar mucho código, los PRs crecen, la revisión se vuelve superficial y los defectos llegan a producción.

    • Mantén los límites de WIP y un tamaño máximo de PR acordado en las políticas del tablero.
    • Si el tiempo de revisión sube o el code review se vuelve la columna cuello de botella, el problema no se resuelve generando más rápido.

    IA.6 Cuidar los roles y el aprendizaje¶

    • Personas junior: necesitan escribir, depurar y entender código para crecer. Acuerda espacios sin asistente o con explicación obligatoria, y pairing con personas senior.
    • Tech Lead: pasa más tiempo revisando y cuidando la arquitectura; reparte la revisión para que no se vuelva un cuello de botella.
    • QA: se enfoca más en criterios de aceptación, pruebas exploratorias y en revisar la calidad de las pruebas generadas.
    • PO: puede usar IA para preparar hallazgos y borradores de historias, pero la conversación con usuarios no se delega.

    IA.7 Acordar el uso de IA con proveedores¶

    Incluye en el contrato (ver Gobierno con proveedores):

    • Qué herramientas puede usar el proveedor y con qué datos del cliente.
    • Que el código generado es propiedad del cliente y cumple las licencias permitidas.
    • Que el proveedor declara el uso de IA y mantiene la revisión humana.
    • Que la tarifa y los niveles de servicio se gobiernan por outcomes y métricas de flujo, no por volumen de código o de horas.

    Assessment de madurez¶

    Fase: 0 (y cada 6 meses para medir evolución) · Duración: 2 a 3 semanas · Facilita: Scrum Master o Agile Coach

    Cuestionario para diagnosticar una célula existente en seis dimensiones. El resultado indica qué fases de la guía reforzar primero.

    Calculadora

    Registra los puntajes en la calculadora de madurez: genera el radar, detecta brechas entre la autoevaluación y lo observado, y propone el orden de fases.

    Cómo se aplica¶

    Principios¶

    • Evidencia antes que opinión. Cada puntaje debe apoyarse en datos o en algo observado. Si no hay evidencia, se puntúa bajo y se anota qué falta.
    • Dos miradas. El equipo se autoevalúa y el facilitador puntúa lo observado. Las diferencias de más de 1 punto son lo más valioso del ejercicio.
    • No es una evaluación de personas. Se evalúa el sistema de trabajo. Los resultados nunca se usan para comparar equipos ni para evaluar desempeño individual.
    • Si no aplica, se marca N/A y no cuenta en el promedio.

    Cost of Delay y WSJF¶

    Fase: 1 y 3 · Origen: Don Reinertsen (Cost of Delay, CD3), SAFe (WSJF) · Duración: 60–90 min por sesión de priorización

    En la Fase 1 priorizas hipótesis por riesgo × valor. Cuando ya hay varios ítems validados o comprometidos que compiten por la misma capacidad, necesitas otra pregunta: ¿cuánto nos cuesta no tenerlo? Esa es la priorización económica.

    Qué es Cost of Delay¶

    El Cost of Delay (CoD) es el valor que se pierde por cada unidad de tiempo que un ítem no está en producción: ingresos no capturados, ahorros que no llegan, multas, riesgo que sigue abierto. Cambia la conversación de "¿qué es más importante?" a "¿qué es más caro esperar?".

    Perfiles de urgencia¶

    No todos los ítems pierden valor igual en el tiempo. El perfil define la clase de servicio:

    Perfil de urgencia Cómo se comporta el CoD Clase de servicio
    Crítico e inmediato Costo alto desde el primer minuto (incidente, caída) Expedito
    Fecha límite Bajo hasta una fecha, luego muy alto o pérdida total (regulación, campaña) Fecha fija
    Lineal Constante por semana de espera (nueva funcionalidad con demanda) Estándar
    Diferido Casi nulo hoy, crece más adelante (deuda técnica, obsolescencia) Intangible

    Fecha fija no se prioriza solo con WSJF

    Para un ítem de fecha fija, lo que importa es cuándo empezarlo: fecha límite menos el lead time P85 de ese tipo de ítem. WSJF ordena el resto.

    CD3 y WSJF¶

    CD3 (Cost of Delay Divided by Duration) usa valores económicos reales:

    CD3 = CoD por semana ÷ duración estimada en semanas
Ej.: 20 000 USD/semana ÷ 4 semanas = 5 000

    Cuando no hay datos económicos confiables, usa WSJF (Weighted Shortest Job First) con escalas relativas:

    CoD  = valor de negocio + criticidad temporal + reducción de riesgo / habilitación de oportunidad
WSJF = CoD ÷ tamaño del trabajo

    Se hace primero lo de mayor WSJF: mucho costo de esperar y poco esfuerzo.

    Ejemplo¶

    Escala Fibonacci modificada: 1, 2, 3, 5, 8, 13, 20. En cada columna, el ítem más bajo vale 1 o 2 y el resto se puntúa en relación con él.

    Ítem Valor de negocio Criticidad temporal Riesgo / oportunidad CoD Tamaño WSJF Orden
    Alertas de pago por SMS 8 3 2 13 3 4,33 1
    Actualizar librería de pagos (habilitador) 2 5 13 20 5 4,00 2
    Validación de identidad digital 13 8 5 26 8 3,25 3
    Reporte regulatorio trimestral 5 20 3 28 13 2,15 4
    Rediseño del portal 20 2 3 25 20 1,25 5

    Lectura: el rediseño tiene el mayor valor de negocio, pero es tan grande que conviene partirlo (ver User Story Map) y volver a puntuar cada parte. El reporte regulatorio es de fecha fija: se agenda según su fecha de inicio, aunque su WSJF sea medio.

    Cómo usarlo¶

    Con negocio

    • Puntúa en grupo: PO, patrocinador y personas de negocio dan valor y criticidad; el equipo da el tamaño.
    • Puntúa columna por columna, no ítem por ítem, para mantener la comparación relativa.
    • Revisa el orden en cada reposición o planificación; el CoD cambia con el tiempo.

    Con compras y proveedores

    • Usa el CoD para justificar capacidad adicional o un expedito: "esperar 4 semanas cuesta X".
    • En contratos por outcomes, acuerda que el orden del backlog lo define el cliente con WSJF visible, no el proveedor según su conveniencia (ver Gobierno con proveedores).
    • Compara ofertas por costo de esperar + costo de construir, no solo por tarifa.

    Advertencias¶

    WSJF ordena, no decide

    • Es una escala relativa: un 13 no vale "13 de algo". No sumes ni compares WSJF entre backlogs distintos.
    • Evita la falsa precisión: discutir si es 4,33 o 4,00 es perder el tiempo. Lo útil son los grupos (alto, medio, bajo) y la conversación.
    • No reemplaza la validación de hipótesis: un ítem con WSJF alto basado en una suposición sin validar sigue siendo una apuesta. Valídala primero en la Fase 1.
    • Si todo tiene criticidad 20, nadie está diciendo la verdad: exige un ítem de referencia en 1.

    Estructura¶

    Ejemplo¶

    Ahora Siguiente Después
    Clientes abandonan la solicitud de crédito en la carga de documentos. Outcome (MVO): 20 % completa la solicitud sin llamar al call center. Iniciativas: formulario guiado, validación automática de documentos. Ejecutivos dedican 40 % de su tiempo a trámites. Outcome: bajar a 20 %. Opciones: panel de solicitudes, notificaciones de estado; por validar con 5 ejecutivos. Clientes con crédito vigente no vuelven a pedir. Oportunidad a explorar: ofertas preaprobadas. Sin solución definida.

    Revisión¶

    Instancia Qué se hace con el roadmap
    Revisión con negocio (cada sprint o entrega) Mostrar datos del outcome en "Ahora". ¿Se logró?, ¿se persevera, se pivota o se para? Mover tarjetas de "Siguiente" a "Ahora" cuando hay capacidad y evidencia.
    Comité directivo trimestral Revisar outcomes contra metas de negocio, repriorizar "Siguiente" y "Después", decidir apuestas. Registrar la decisión.

    Una tarjeta sale del roadmap cuando se logra el outcome

    No cuando se entrega la funcionalidad. Si se entregó y la métrica no se movió, la tarjeta sigue o se decide pivotar.

    Responder "¿para cuándo?"¶

    Responde con pronósticos probabilísticos (Fase 5, sección 5.4), no con estimaciones en horas:

    • Ahora: Monte Carlo sobre los ítems restantes y el throughput histórico. "Con 85 % de probabilidad, el formulario guiado está en producción antes del 14 de noviembre."
    • Siguiente: rango por trimestre según capacidad disponible. "Si mantenemos el throughput, empezamos en enero; el alcance depende de lo que validemos."
    • Después: sin fecha. "Es una apuesta; se decide en el comité trimestral con la evidencia que tengamos."

    Fechas fijas reales

    Si hay una fecha externa (regulatoria, contractual), la tarjeta se marca como Fecha fija y se inicia con margen según el lead time P85, igual que en las clases de servicio.

    Seguridad y cumplimiento en el flujo¶

    Fase: 2 y 4 · Origen: DevSecOps, OWASP, STRIDE · Duración: configuración inicial en el sprint 0; luego continuo

    En banca, salud o sector público, la seguridad suele llegar al final como una auditoría que bloquea el paso a producción. Esta herramienta la mueve dentro del flujo: se piensa en el refinamiento, se verifica en el pipeline y la evidencia se genera sola. Complementa el pipeline de la Fase 2 y el checklist de paso a producción.

    Principio

    Un control de seguridad que depende de que alguien se acuerde no es un control. Automatiza lo verificable y deja a las personas lo que requiere juicio.

    Threat modeling liviano¶

    En el refinamiento de cada épica, y de las historias que tocan datos sensibles, autenticación o integraciones, dedica 10 minutos a estas preguntas (STRIDE):

    Amenaza Pregunta
    Suplantación ¿Alguien puede hacerse pasar por otro usuario o sistema?
    Tampering (alteración) ¿Se pueden modificar datos en tránsito o en reposo sin que lo detectemos?
    Repudio ¿Podemos probar quién hizo qué y cuándo?
    Información expuesta ¿Qué datos se podrían filtrar, en logs, errores o respuestas?
    Denegación de servicio ¿Qué pasa si llaman esto mil veces por segundo?
    Elevación de privilegios ¿Puede un usuario hacer algo que su rol no permite?

    Cada riesgo relevante se convierte en un criterio de aceptación o en un ítem del backlog. Para decisiones de arquitectura, regístralo en un ADR.

    Controles en el pipeline¶

    Control Qué detecta Cuándo corre Bloquea si
    Escaneo de secretos Claves y tokens en el código Pre-commit y cada PR Encuentra cualquier secreto
    SAST Vulnerabilidades en el código propio Cada PR Hallazgo crítico o alto nuevo
    SCA / dependencias Librerías con vulnerabilidades o licencias no permitidas Cada PR y diario Crítico con corrección disponible
    Escaneo de imagen Vulnerabilidades en la imagen Docker y su base Al construir la imagen Crítico con corrección disponible
    SBOM Inventario de componentes de cada versión En cada build de release No se generó
    DAST (opcional) Fallas en la aplicación en ejecución En staging, nocturno Según política

    Bloquea lo nuevo, gestiona lo heredado

    En una célula existente, activar todos los bloqueos de golpe detiene el flujo. Bloquea solo los hallazgos nuevos y trata los heredados como deuda priorizada con SLA.

    Privacidad y datos personales¶

    • Minimización: cada historia que recoge datos personales justifica qué campo necesita y para qué.
    • Ambientes no productivos sin datos reales: usa datos sintéticos o enmascarados. Nunca copies producción a DEV o QA sin anonimizar.
    • Retención: define cuánto tiempo se guarda cada dato y automatiza su borrado.
    • Logs limpios: nada de documentos de identidad, datos de salud, tarjetas ni contraseñas en logs.

    Evidencia automática para auditoría y CAB¶

    Configura el pipeline para que cada release guarde, asociado a su versión:

    • Resultado de pruebas, SAST, SCA y escaneo de imagen.
    • SBOM y digest de la imagen desplegada.
    • PR con revisores y aprobaciones, enlazado al ítem del tablero.
    • Quién desplegó, cuándo y a qué ambiente.

    Con esta evidencia, el CAB revisa solo los cambios de alto riesgo y la auditoría se responde con una consulta, no con semanas de recopilación.

    Definition of Ready y Definition of Done¶

    Fase: 2 y 4 · Acordadas por el equipo, revisadas en retrospectiva cada 1–2 meses.

    Definition of Ready (DoR)¶

    Un ítem puede entrar en desarrollo cuando:

    • Está conectado a un objetivo u outcome del roadmap.
    • Tiene descripción en formato Como [usuario] quiero [acción] para [beneficio].
    • Tiene criterios de aceptación en formato Given / When / Then, revisados por PO, Dev y QA (three amigos).
    • Es lo suficientemente pequeño para completarse en 1 a 3 días.
    • Dependencias identificadas y resueltas (o con fecha).
    • Diseño o UX disponible si aplica.
    • Se sabe cómo medir su uso o efecto (si aplica).

    La DoR no es un contrato

    Úsala como guía de conversación, no como barrera burocrática.

    Definition of Done (DoD)¶

    Un ítem está terminado cuando:

    • Código revisado por al menos una persona (pull request aprobado).
    • Pruebas unitarias y de integración automatizadas y en verde.
    • Análisis estático y de seguridad sin hallazgos críticos (ver seguridad en el flujo).
    • Código generado con IA revisado y probado con el mismo estándar que el resto (ver IA en la célula).
    • Criterios de aceptación verificados (automatizados cuando sea posible).
    • Prueba exploratoria realizada.
    • Documentación técnica actualizada (README, ADR, API).
    • Desplegado en producción (detrás de feature flag si aplica).
    • Monitoreo y alertas configurados para lo nuevo.
    • PO validó el comportamiento.

  Cuando sube un PDF de menos de 5 MB
  Entonces el sistema muestra el documento como "Validado"

    Pronóstico Monte Carlo¶

    Fase: 5 · Origen: Kanban (pronósticos probabilísticos) · Duración: 10 minutos con el historial a mano

    Responde con probabilidades las dos preguntas que negocio hace siempre: ¿cuándo terminamos? y ¿cuánto alcanzamos a entregar? Usa el throughput histórico de la célula en lugar de estimaciones en horas. Es la herramienta de la actividad 5.4 Pronosticar con datos.

    Cómo funciona¶

    1. Tomas el throughput semanal histórico: cuántos ítems terminó la célula cada semana.
    2. La simulación arma un futuro posible eligiendo semanas al azar de ese historial, con reemplazo (una misma semana puede salir varias veces).
    3. Repite el ejercicio 10 000 veces y cuenta los resultados.
    Pregunta Entrada Resultado Cómo leer el 85 %
    ¿Cuándo? N ítems Semanas (y fechas) para terminarlos El 85 % de las simulaciones termina en esa cantidad de semanas o menos
    ¿Cuánto? N semanas Ítems terminados en ese plazo En el 85 % de las simulaciones se alcanza esa cantidad de ítems o más

    Comprométete con el percentil 85, no con el 50: el 50 % es una moneda al aire.

    Supuestos¶

    El pronóstico vale lo que vale el historial. Revisa estos supuestos antes de compartirlo:

    • Sistema estable. El futuro se parece al pasado: mismo equipo, mismas políticas de WIP, sin cambios grandes de contexto. Si cambió la composición de la célula, usa solo las semanas posteriores al cambio.
    • Mismo tipo de ítems. El historial y el backlog por pronosticar tienen ítems de tamaño y naturaleza parecidos. No mezcles historias con épicas ni con incidentes.
    • La división de ítems cambia el pronóstico. Un release de 40 ítems suele terminar con más de 40: al refinar, los ítems se dividen y aparecen otros nuevos. Ajusta N con tu tasa histórica de crecimiento del backlog o vuelve a pronosticar cada semana.
    • Historial reciente y suficiente. Usa entre 8 y 12 semanas recientes. Con menos de 6 la calculadora no simula. Las semanas sin entregas (vacaciones, congelamientos) cuentan como 0 si pueden repetirse.

    Uso en la célula¶

    • Extrae el throughput semanal desde la herramienta de gestión (ítems terminados, no puntos).
    • Pronostica con el percentil 85 y comunica el rango, no una fecha única.
    • Repite el pronóstico cada semana con datos nuevos y muestra cómo se mueve.
    • Registra el acierto: qué porcentaje de entregas cae dentro del rango pronosticado (métrica de la Fase 5).

    Antipatrón

    Convertir el percentil 50 en compromiso, o usar el pronóstico para presionar al equipo. El pronóstico describe el sistema; si no gusta el resultado, se cambia el sistema (WIP, tamaño de los ítems, dependencias), no el número.

    Retrospectiva basada en datos¶

    Fase: 5 y 6 · Duración: 60 a 90 minutos

    Estructura¶

    Momento Tiempo Actividad
    1. Check-in 5 min Happiness Door o una palabra para describir el periodo
    2. Revisar acciones anteriores 5 min ¿Se hicieron? ¿Tuvieron efecto en la métrica esperada?
    3. Mirar los datos 15 min CFD, scatterplot de cycle time, throughput, bloqueos, incidentes
    4. Generar ideas 15 min ¿Qué explica lo que vemos? (5 porqués sobre el patrón más relevante)
    5. Decidir 15 min Elegir 1 o 2 experimentos de mejora con métrica esperada
    6. Cierre 5 min ROTI (retorno del tiempo invertido)

    Preguntas guía sobre los datos¶

    • ¿Dónde se acumula el trabajo en el CFD? ¿Qué columna se ensancha?
    • ¿Qué ítems quedaron sobre el percentil 85? ¿Qué tienen en común?
    • ¿Cuáles fueron los motivos de bloqueo más frecuentes?
    • ¿Cuánto trabajo no planificado entró? ¿De dónde vino?
    • ¿Hubo incidentes? ¿Qué nos enseñaron?
    • ¿Cómo cambió el ánimo del equipo respecto al periodo anterior?

    Value Stream Mapping¶

    Fase: 6, cada 3–6 meses · Duración: taller de 3 a 4 horas · Participantes: PO, Tech Lead, equipo, y quienes intervienen fuera de la célula (aprobadores, operaciones, seguridad)

    Mapea el flujo de valor completo, de la idea al usuario, para encontrar dónde espera el trabajo (Fase 6, sección 6.2).

    Pasos del taller¶

    1. Acotar el flujo: un tipo de ítem (por ejemplo, historia estándar), con punto de inicio y de fin claros.
    2. Listar las etapas reales, incluidas las que ocurren fuera de la célula (aprobaciones, comités, ventanas de despliegue).
    3. Anotar por etapa el tiempo de proceso (trabajo activo) y el tiempo de espera previo. Usa medianas de los datos, no el mejor caso.
    4. Calcular lead time total y eficiencia de flujo.
    5. Marcar las 2–3 esperas más grandes y buscar su causa (5 porqués).
    6. Dibujar el mapa futuro y convertir cada cambio en un experimento del backlog de mejora.

    El mapa futuro es una dirección, no un plan. Lleva los cambios al backlog de mejora respetando el máximo de 1 a 2 mejoras en curso.

    De dónde sacar los datos¶

    • Jira: el historial de cambios de estado (changelog) de cada issue, vía exportación, API o un reporte de control. Calcula el tiempo en cada estado.
    • Azure DevOps: Analytics (OData o Power BI) con las revisiones del work item y la fecha de cada cambio de estado.
    • Pipeline: tiempos de espera entre aprobación y despliegue.
    • Fuera de las herramientas: las aprobaciones por correo o comité se reconstruyen con fechas de 10–20 ítems recientes.

    Política de escalamiento¶

    1. Toda dependencia con fecha necesaria se registra al identificarse, no cuando bloquea.
    2. Si a 5 días hábiles de la fecha necesaria no está "En curso", los PO de ambas células la conversan en 48 horas.
    3. Sin acuerdo, se lleva a la sincronización de PO de esa semana.
    4. Si sigue sin resolverse o afecta un outcome del roadmap, se escala a la revisión de operaciones o al patrocinador, con las opciones y su costo de demora.

    Revisión en la revisión de operaciones¶

    • Dependencias bloqueadas o en riesgo, de derecha a izquierda del tablero.
    • Métricas del periodo y su tendencia.
    • Pares de células con dependencias recurrentes: candidatas a rediseño.

    Métricas¶

    Métrica Cálculo Uso
    % de ítems bloqueados por dependencias externas Ítems terminados que estuvieron bloqueados por otra célula o tercero ÷ ítems terminados Medir el acoplamiento entre células
    Tiempo bloqueado por dependencia Días en estado Bloqueado, en percentil 85 Costo de la dependencia en el lead time
    Dependencias entregadas a tiempo Entregadas antes de la fecha necesaria ÷ total Confiabilidad entre células

    Si más del 20 % de los ítems se bloquea por dependencias, el problema es de diseño organizacional, no de coordinación.

    Cómo reducir dependencias¶

    • Dividir por dominio o flujo de valor, no por capa técnica: cada célula lleva un cambio de punta a punta.
    • Plataforma como autoservicio: ambientes, pipelines y datos de prueba sin tickets.
    • Contratos de API versionados para que cada célula avance sin esperar a la otra.
    • Inner source: la célula que necesita el cambio lo hace en el código de la otra, con su revisión.
    • Mover personas o conocimiento cuando la dependencia es de una sola persona.

    Antipatrón

    Un tablero de dependencias que crece cada mes no es éxito de coordinación: es la señal de que las células están mal cortadas.

    Caso · Crear una célula para crédito en línea¶

    Caso ficticio

    Organización, personas y cifras inventadas con fines ilustrativos. Ver Casos de ejemplo.

    Contexto¶

    Una financiera mediana ofrece créditos de consumo. Su web tiene un formulario que solo captura datos: el call center llama al cliente, pide documentos por correo y arma la solicitud. El patrocinador (gerente de canales digitales) quiere bajar el costo por solicitud y el tiempo de respuesta. No hay equipo ni producto.

    Punto de partida¶

    • 100 % de las solicitudes pasan por el call center.
    • Sin pipeline, sin ambientes para el nuevo producto y sin datos de uso de la web.
    • Equipo asignado en la semana 1: PO, SM / Coach, Tech Lead, 3 desarrolladores, QA y UX (8 personas dedicadas).

    Siguiendo Cómo usar la guía, el producto no está validado: Fase 0 → 1 completa con experimentos antes de acelerar.

    Recorrido¶

    Semanas 1–2 · Fase 0¶

    Con la Fase 0 se escribió el objetivo en una frase: "Que un cliente pueda solicitar un crédito de consumo sin depender del call center". El equipo hizo su Team Canvas y un Delegation Board donde el equipo decide el stack y el PO decide el orden del backlog. Todas las personas tenían accesos el día 3.

    Semanas 2–6 · Fase 1¶

    Siete entrevistas de problema y el Lean Canvas llevaron al MVO:

    El 30 % de las solicitudes iniciadas en la web se completa sin contacto con el call center, dentro de las 8 semanas siguientes a liberar el MVP al 100 % del tráfico.

    El MVP se construyó en historias de 1 a 3 días. Siguiendo la Fase 4 y el checklist de paso a producción, se liberó con feature flag al 10 % del tráfico en la Semana 12 y al 100 % al cierre de la Semana 13. El plazo del MVO vence, por tanto, en la Semana 21.

    2. Regla 1 · Primero el flujo. Flujo observado es 2,2 (menor a 2,5): la Fase 3 va primero, aunque Relación con negocio tiene el puntaje más bajo (1,6).
    3. Regla 2 · Riesgo de producción. Calidad es 1,8 (menor a 2): se refuerza con la Fase 2 y la Fase 4 antes de aumentar el ritmo de entrega.
    4. Regla 4 · Máximo dos frentes. Flujo y Calidad ocupan los dos frentes. Relación con negocio (1,6) y Producto (2,2), siguientes por la regla 3, esperan.

    El orden se presentó a la PO y al patrocinador, que lo aceptaron con una condición: revisar el avance en el mes 3.

    Mes 1 · Fase 3: hacer visible y limitar el flujo¶

    • Todo pedido de soporte entra al tablero; el correo y el chat dejan de ser canales de entrada.
    • Con 49 % de demanda no planificada (entre 20 % y 50 %), se eligió Scrumban: cadencia de 2 semanas para lo planificado y flujo con WIP para el resto. Por estar cerca del 50 %, el ADR de proceso fija revisarlo en el mes 3.
    • Capacidad reservada: 50 % producto, 40 % soporte, 10 % deuda. Clases de servicio y WIP en las políticas del tablero.

    Meses 2–4 · Fases 2 y 4: calidad y lotes pequeños¶

    • Pruebas automatizadas de los tres flujos críticos (pago, boleta, reclamo) en el pipeline.
    • Despliegue automatizado hasta staging; la DoD pasa a incluir "desplegado en producción".
    • Release quincenal en el mes 2 y semanal desde el mes 3, con el checklist de paso a producción.
    • Postmortem sin culpa de cada incidente severo. Los cinco defectos recurrentes que más soporte generaban entraron como deuda con capacidad reservada.

    Desde la Semana 3 · Fase 5: línea base y revisión de servicio¶

    La línea base salió del historial (ver Fase 5). Cada mes, la revisión de servicio con el gestor de cuenta del proveedor compara las métricas contra la línea base, como propone Gobierno con proveedores.

    Resultados¶

    Periodo Lead time P85 Despliegues Change failure rate No planificado
    Línea base (3 meses) 64 días 2 por mes (6) 33 % (2 de 6) 49 %
    Mes 1 52 días 2 50 % (1 de 2) 47 %
    Mes 2 41 días 3 33 % (1 de 3) 44 %
    Mes 3 30 días 5 20 % (1 de 5) 38 %
    Mes 4 24 días 6 17 % (1 de 6) 35 %
    Mes 5 19 días 8 13 % (1 de 8) 33 %

    En el mes 3 el trabajo no planificado bajó a 38 %; Scrumban se mantuvo y la reserva para soporte se ajustó a 30 % (60 % producto, 10 % deuda).

    Assessment reaplicado en el mes 6 (observado): Flujo 3,4 · Ingeniería 3,0 · Calidad 3,0 · Equipo 3,4 · Producto 2,4 · Relación con negocio 1,8. Ya no aplican las reglas 1 y 2, así que por la regla 3 los dos nuevos frentes son Relación con negocio (pasar el contrato de horas a niveles de servicio por flujo) y Producto (Fase 1).

    Lecciones¶

    • La brecha valió más que el puntaje. Sin el taller de la Semana 3, el equipo habría rechazado la Fase 3 porque "el flujo ya funciona".
    • El puntaje más bajo no siempre va primero. Mejorar la relación con negocio sin flujo visible no habría tenido con qué medirse.
    • El change failure rate empeoró en el mes 1 (1 de 2) antes de mejorar: con tan pocos despliegues, un solo fallo pesa mucho. Se leyó la tendencia, no el mes aislado.
    • Bajar el soporte fue consecuencia de la calidad, no de una meta de soporte.

    Caso · Traspaso de proveedor a equipo interno¶

    Caso ficticio

    Organización, personas y cifras inventadas con fines ilustrativos. Ver Casos de ejemplo.

    Contexto¶

    Una aseguradora tiene su app de denuncia de siniestros en manos de un proveedor desde hace tres años: 6 personas en una célula dedicada, con PO del cliente. La aseguradora decide internalizarlo por ser central en su estrategia digital. El contrato incluye un plan de salida con traslape de hasta 6 meses y horas de respaldo. Se sigue el capítulo de Traspaso a equipo interno con el plan de traspaso.

    Punto de partida¶

    • Equipo interno: Tech Lead contratado en la Semana 1; cuatro personas más (3 desarrolladores y 1 QA) se incorporan en la Semana 3.
    • Assessment reciente: Ingeniería 3,2 y EQ5 (conocimiento) en 2, lo que anticipa un traslape largo.
    • Línea base de las 12 semanas previas (ver Fase 5):
    Métrica Línea base
    Lead time P85 11 días
    Throughput 6 ítems por semana
    Despliegues 2 por semana (24 en 12 semanas)
    Change failure rate 8 % (2 de 24)

    Recorrido¶

    Semanas 1–3 · Etapa 1: Preparar¶

    El inventario de activos tuvo un hallazgo problemático:

    Activo Titular actual Titular final Estado en Semana 3
    Repositorios Org de GitHub del proveedor Cliente Transferidos
    Pipeline de despliegue Proveedor Cliente Transferido con los repositorios
    Cuenta cloud de producción Proveedor (facturada y re-facturada al cliente) Cliente En migración
    Dominio y certificados Cliente Cliente Sin cambio
    Gestor de secretos Dentro de la cuenta cloud del proveedor Cliente En migración
    Monitoreo y alertas Cuenta SaaS del proveedor Cliente Nueva cuenta creada

    La cuenta cloud incumplía lo acordado en Gobierno con proveedores: "activos a nombre del cliente desde el primer día". Siguiendo la regla de transferir la propiedad antes que el conocimiento, se movió la cuenta a la organización cloud del cliente y se rotaron todas las credenciales. Terminó en la Semana 6, ya en shadowing, sin corte de servicio.

    El PO pospuso la migración de base de datos prevista para el trimestre: congelar el riesgo, no el producto.

    Semanas 4–7 · Etapa 2: Shadowing¶

    Un solo tablero y las mismas ceremonias. Cada persona interna con una contraparte del proveedor. En la Semana 5 todas levantaron el entorno local de cero (tiempo medio: 3 h, que bajó a 40 min al reescribir el README). En la Semana 6 el equipo interno desplegó un cambio trivial a staging. Se cumplieron los criterios para avanzar.

    Semanas 8–15 · Etapa 3: Reverse shadowing (extendida)¶

    El equipo interno llevó historias a producción con revisión del proveedor desde la Semana 8 y ejecutó su primer rollback en la Semana 10. El plan era cerrar esta etapa en la Semana 12. En la revisión semanal de avance no se cumplían dos criterios:

    • Restore de backup ejecutado por el equipo interno: falló en la Semana 11 porque el runbook apuntaba a la cuenta cloud antigua.
    • Todas las áreas con al menos una persona interna en nivel 2: Monitoreo y guardia seguía en nivel 1.

    El PO extendió la etapa 3 semanas con las horas de respaldo del contrato. El restore se repitió con éxito en la Semana 13 y el runbook quedó corregido en el repositorio del cliente.

    Mapa de conocimiento (persona interna 1 / persona interna 2; niveles de 0 a 3):

    Área Semana 3 Semana 7 Semana 12 Semana 15 Semana 23
    Dominio de siniestros 0 / 0 1 / 1 2 / 1 2 / 2 3 / 2
    API y modelo de datos 1 / 0 1 / 1 2 / 2 2 / 2 3 / 2
    Integración con core de pólizas 0 / 0 1 / 0 2 / 1 2 / 1 2 / 2
    Pipeline y despliegue 1 / 0 1 / 1 2 / 2 3 / 2 3 / 2
    Monitoreo y guardia 0 / 0 1 / 0 1 / 1 2 / 1 2 / 2

    Semanas 16–23 · Etapa 4: Operación autónoma¶

    El equipo interno opera solo; el proveedor responde a demanda en menos de 4 horas. Cada consulta quedó en el registro del plan de traspaso:

    Semana 16 17 18 19 20 21 22 23
    Consultas al proveedor 7 5 3 2 1 0 0 0

    De las 18 consultas, 11 revelaron documentación faltante y generaron un runbook o un ADR. En la Semana 19 el equipo interno resolvió su primer incidente severo sin ayuda.

    Semanas 24–25 · Etapa 5: Cierre¶

    Inventario verificado, accesos del proveedor retirados, acta de cierre firmada, retrospectiva de traspaso y assessment reaplicado. El equipo hizo un nuevo Team Canvas y retomó desde la Fase 0.

    Resultados¶

    Periodo Lead time P85 Throughput Change failure rate Despliegues del equipo interno
    Línea base 11 días 6 por semana 8 % (2 de 24) 0 %
    Etapa 2 (4 semanas) 11 días 6 por semana 0 % (0 de 8) 0 %
    Etapa 3 (8 semanas) 13 días 5 por semana 13 % (2 de 16) 63 % (10 de 16)
    Etapa 4 (8 semanas) 10 días 6 por semana 6 % (1 de 17) 100 % (17 de 17)

    Las métricas se degradaron en la etapa 3, como era esperable. En las semanas 20–23 estuvieron iguales o mejores que la línea base: se cumplió el criterio de salida de 4 semanas.

    El traspaso duró 25 semanas: dentro del rango de referencia de 3 a 6 meses, pero 3 semanas más de lo planificado.

    Lecciones¶

    • Revisa la titularidad de los activos antes de firmar el plan. La cuenta cloud a nombre del proveedor costó 3 semanas y fue la causa indirecta del restore fallido.
    • Extender a tiempo es más barato que un incidente. Las 3 semanas extra se pagaron con horas de respaldo ya contratadas.
    • Las consultas al proveedor son un mapa de huecos. 11 de 18 terminaron en documentación nueva.
    • Monitoreo y guardia fue el área más lenta. Se aprende en incidentes reales, que no ocurren a demanda: conviene simularlos desde el shadowing.

    Ended: Casos de ejemplo

    Glosario¶

    ADR
    Architecture Decision Record. Documento breve que registra una decisión, su contexto y consecuencias.
    Agente de IA
    Herramienta de IA que ejecuta tareas de varios pasos con cierta autonomía (abrir PRs, correr comandos) bajo permisos definidos.
    Asistente de código
    Herramienta de IA que sugiere o genera código dentro del editor o del flujo de revisión.
    Blue / Green
    Estrategia de despliegue con dos ambientes de producción idénticos; se cambia el tráfico de uno a otro y se vuelve atrás al instante si falla.
    Bus factor
    Cantidad de personas que tendrían que faltar para que el equipo no pueda seguir operando una parte del sistema.
    C4
    Modelo de diagramas de arquitectura en cuatro niveles: contexto, contenedores, componentes y código.
    CAB
    Change Advisory Board. Comité que aprueba cambios a producción.
    Canary
    Liberación gradual a un porcentaje pequeño del tráfico para detectar problemas antes de llegar a todos los usuarios.
    CD3
    Cost of Delay Divided by Duration. Prioriza dividiendo el costo de demora por semana entre la duración estimada.
    CFD
    Cumulative Flow Diagram. Gráfico que muestra la cantidad de ítems por estado a lo largo del tiempo.
    Change failure rate
    Porcentaje de despliegues que causan una falla en producción que requiere corrección.
    Clase de servicio
    Política que define cómo se trata un tipo de ítem según su urgencia y costo de demora.
    Cost of Delay
    Valor que se pierde por cada unidad de tiempo que un ítem no está en producción.
    Cycle time
    Tiempo desde que se empieza a trabajar en un ítem hasta que se termina.
    Dependencia externa
    Trabajo, recurso o aprobación que una célula necesita de otra célula o de un tercero para terminar un ítem.
    DoR / DoD
    Definition of Ready y Definition of Done. Acuerdos sobre cuándo un ítem puede empezar y cuándo está terminado.
    DORA
    Cuatro métricas de desempeño de entrega de software: frecuencia de despliegue, lead time de cambios, change failure rate y tiempo de recuperación.
    Eficiencia de flujo
    Proporción del lead time en que un ítem recibe trabajo activo.
    Exit plan
    Plan de salida acordado en el contrato con un proveedor: traslape, entregables, propiedad intelectual y continuidad del servicio.
    Expedito
    Clase de servicio para urgencias, como un incidente crítico: se salta la fila y tiene un límite de WIP de 1.
    Fake door
    Experimento que muestra una opción que aún no existe para medir cuántas personas la eligen.
    Feature flag
    Mecanismo para activar o desactivar funcionalidades sin desplegar código nuevo.
    Happiness Door
    Técnica de Management 3.0 en que cada persona marca cómo se siente al cerrar una reunión, para ver tendencias de ánimo.
    Impact Mapping
    Técnica que conecta una meta de negocio con actores, impactos esperados en su comportamiento y entregables.
    Kudo Cards
    Tarjetas de reconocimiento entre pares de Management 3.0.
    Lead time
    Tiempo desde que se compromete un ítem hasta que está disponible en producción.
    Mapa de conocimiento
    Matriz que cruza áreas funcionales, técnicas y operativas con las personas que las dominan y su nivel. Mide el avance de un traspaso.
    Matriz poder / interés
    Herramienta que ubica a cada stakeholder según su capacidad de influir y su interés en el producto, para definir cómo involucrarlo.
    Métrica de vanidad
    Indicador que crece sin reflejar valor, como las líneas de código generadas.
    Monte Carlo
    Simulación que usa datos históricos de throughput para pronosticar fechas o alcance con probabilidades.
    Moving Motivators
    Juego de Management 3.0 para conocer qué motiva a cada persona y cómo lo afecta un cambio.
    MVO
    Minimum Viable Outcome. El cambio mínimo y medible en el comportamiento del usuario o negocio que valida una apuesta.
    MVP
    Minimum Viable Product. El producto mínimo construido para aprender si se logra el MVO.
    Offboarding
    Salida planificada de una persona, con traspaso de responsabilidades, conocimiento y accesos.
    Personal Map
    Herramienta de Management 3.0 para conocer el contexto personal de cada integrante del equipo.
    Postmortem
    Análisis sin culpa de un incidente para entender sus causas y definir acciones que eviten que se repita.
    Reverse shadowing
    Etapa de un traspaso en que el equipo receptor ejecuta el trabajo real y el equipo saliente revisa y corrige.
    Roadmap Ahora / Siguiente / Después
    Roadmap en tres horizontes de certeza decreciente, expresado en problemas y outcomes en lugar de fechas y funcionalidades.
    SAST
    Static Application Security Testing. Análisis estático del código propio en busca de vulnerabilidades.
    SBOM
    Software Bill of Materials. Inventario de los componentes incluidos en cada versión.
    SCA
    Software Composition Analysis. Análisis de dependencias de terceros por vulnerabilidades y licencias.
    Scrumban
    Combinación de la cadencia de Scrum con la gestión de flujo y límites de WIP de Kanban.
    Shadowing
    Etapa de un traspaso en que el equipo receptor observa al equipo saliente trabajar sobre casos reales y pregunta.
    SLE
    Service Level Expectation. Pronóstico basado en datos del tiempo en que se completará un ítem (ej. 85 % en 10 días).
    STRIDE
    Modelo de amenazas: suplantación, alteración, repudio, exposición de información, denegación de servicio y elevación de privilegios.
    Swarming
    Práctica en que varias personas del equipo se juntan sobre un mismo ítem para destrabarlo o terminarlo antes de empezar otro.
    Threat modeling
    Análisis de cómo puede atacarse una funcionalidad antes de construirla.
    Three amigos
    Conversación entre PO, desarrollo y QA para acordar los criterios de aceptación de una historia antes de construirla.
    Throughput
    Cantidad de ítems terminados por unidad de tiempo.
    Time to first deploy
    Tiempo desde que una persona se incorpora hasta que su primer cambio llega a producción.
    Timebox
    Duración máxima fija de una reunión o actividad; al cumplirse, termina.
    Traslape
    Periodo en que el equipo saliente y el entrante trabajan juntos para transferir conocimiento sin cortar el servicio.
    Trunk-based development
    Práctica de integrar cambios a la rama principal al menos una vez al día.
    Value Stream Map
    Diagrama del flujo de valor de la idea al usuario, con tiempos de proceso y de espera por etapa.
    Ventana de solapamiento
    Franja horaria en que todas las personas de una célula distribuida están disponibles.
    Walking skeleton
    Implementación mínima de punta a punta que atraviesa toda la arquitectura y llega a producción.
    WIP
    Work in Progress. Trabajo iniciado y no terminado.
    WSJF
    Weighted Shortest Job First. Prioriza dividiendo el Cost of Delay entre el tamaño del trabajo, con escalas relativas.

    Flujo del mantenedor: directo a main¶

    El mantenedor publica los cambios directamente en main. Cada push dispara el workflow, que valida el sitio en modo estricto y lo publica en GitHub Pages.

    flowchart LR
    P[git pull] --> E[Editar docs/]
    E --> C[Actualizar changelog]
    C --> V[mkdocs build --strict]
    V --> G[commit + push a main]
    G --> W[Publicación automática]

    Preparar el entorno (una sola vez)¶

    python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

    Cada cambio¶

    source .venv/bin/activate      # en cada terminal nueva
git pull                       # trae ediciones hechas desde la web
# editar archivos en docs/ y actualizar docs/changelog.md
mkdocs serve                   # opcional: ver en http://127.0.0.1:8000
mkdocs build --strict          # debe terminar sin WARNING ni ERROR
git add .
git commit -m "Descripción corta del cambio"
git push

    Si cambió requirements.txt

    Vuelve a correr pip install -r requirements.txt dentro de .venv después del git pull.

    Publicar una versión¶

    Cuando el changelog tiene una versión nueva cerrada:

    git tag -a vX.Y.Z -m "vX.Y.Z: resumen"
git push origin vX.Y.Z
gh release create vX.Y.Z --verify-tag --title "vX.Y.Z: resumen" --notes "…sección del changelog…"
    1. Agrega la fila de la versión en docs/versiones.md y cambia la anterior a Archivada con su enlace.
    2. El push del tag vuelve a publicar el sitio y crea la copia archivada en versiones/vX.Y.Z/.

    Sin revisión previa

    Al publicar directo en main, el build estricto en local es la única barrera antes de que el cambio llegue al repositorio. Si el workflow falla, la web no se actualiza y la pestaña Actions muestra el error.

    Contribuciones de otras personas¶

    Quien no mantiene el repositorio contribuye por pull request:

    1. Proponer una mejora o reportar un error: abrir un issue con la plantilla Propuesta de mejora, Error o enlace roto o Caso de una célula real.
    2. Editar desde la web: el ícono de lápiz ✏️ de cada página crea un pull request automáticamente.
    3. Cambios grandes: hacer fork, editar en local y abrir un pull request.

    El workflow valida el build de cada pull request antes del merge. Además, cada lunes revisa los enlaces externos; ese chequeo es informativo y no bloquea la publicación.
